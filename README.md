# Patched CEF for IronRDP

This repository holds ordered patches and build automation, not a CEF fork.
GitHub Actions builds pinned upstream CEF/Chromium with the IronRDP patches on
free GitHub-hosted runners and publishes the unmodified CEF `--minimal`
distributions as GitHub prereleases for a cef-rs fork to consume.

CI verifies patch identity, pinned checkouts and the patched `libcef` exports.
Before publishing, it also loads each library on a native runner and checks
the disabled-clipboard getters without initializing CEF. **It does not run
IronRDP's native tests.** Only the upstream IronRDP custom build on macOS
ARM64 has been validated at runtime; run those tests (`e2e.py`, `clipboard.py`,
`devices.py`, `shutdown.py`) before relying on any other platform.

## Building in GitHub Actions

Dispatch **Build patched CEF** (`build.yml`) on `master`. Inputs:

- `targets`: JSON list from `linux-x64`, `linux-arm64`, `windows-x64`,
  `windows-arm64`, `macos-x64`, `macos-arm64` (default: all six).
- `skip-macos`: drop the macOS targets from `targets`. macOS builds are
  deferred, not removed; leave this unset to build macOS again.
- `publish`: create one prerelease when every requested target succeeds.
- `stage-minutes`: build time per stage (default 280; lower only to test
  resumption).
- `resume-run`: an earlier run ID; each target's stage 1 restores that run's
  newest saved tree instead of syncing (use after a runner loss or failure).
  A finished build whose distribution step fails also saves its tree, so
  resuming it retries only the distribution.
  Trees must have matching host-architecture metadata; older trees without it
  and Intel macOS trees cannot resume on Apple Silicon.

A Chromium build takes far longer than the 6-hour hosted job limit, so each
target runs as a chain of resumable stages generated by `scripts/stages.ps1`
into `build-target.yml` (regenerate with `pwsh scripts/stages.ps1`):

1. **Stage 1** clones depot_tools at its pin and bootstraps it, runs the pinned
   `automate-git.py --no-build --no-distrib` (verified by blob hash) without
   Chromium history, verifies all three checkouts, applies the patches, then
   runs CEF's `gclient_hook.py` so CEF's own patches and `gn gen` follow ours.
2. **Every stage** runs ninja (`cefclient` on macOS, `cefclient`, `bootstrap`
   and `bootstrapc` on Windows, `cefsimple` and `chrome_sandbox` on Linux, where
   the sysroot build has no GTK for `cefclient`) until its deadline, then stops it
   gracefully so its log stays consistent. Ninja runs at most one job per 2 GiB
   of memory, and never more than its default of CPUs + 2: 3 jobs on the
   7 GB macOS runners, 6 on Linux and Windows (set `CEF_NINJA_JOBS` to override).
   Memory and swap use are logged every 10 minutes while ninja runs.
3. **Unfinished** stages save the whole tree as split tar+zstd artifacts that
   preserve nanosecond mtimes (`scripts/tree.ps1`; on Windows it streams with
   .NET `TarWriter`/`TarReader` because the system bsdtar crashes on Chromium
   trees); the next stage restores them at the same
   absolute path and ninja resumes.
4. **The finishing** stage runs `make_distrib.py --minimal`, then
   `scripts/release.ps1` checks the standard archive name and top-level
   directory, and verifies the 14 patched exports in `libcef`. The candidate
   archive, `SHA256SUMS` and `manifest.json` are uploaded.
5. The **release** workflow (`release.yml`) first checks that each patched
   library loads on a native runner. It checks every candidate's checksum and
   that its manifest carries this checkout's pins and patch blobs and matches
   the archive actually smoke-tested, imports each archive with the pinned
   cef-rs exporter, and checks the resulting library's architecture and
   essential files. It then publishes a prerelease tagged
   `cef-<cef version>-patched.<run id>`. Dispatch **Publish release** directly
   with a JSON list of run IDs to assemble targets built by different runs
   (earlier runs win). Set `dry-run` to verify without publishing, and
   `skip-macos` to release only Linux and Windows while macOS is pending.

Runners: `ubuntu-24.04` (arm64 is cross-compiled with CEF's sysroot),
`windows-2025` (installs Windows SDK 10.0.28000 required by Chromium 156) and
`macos-26` Apple Silicon for both macOS architectures (Xcode 26). The build is an official configuration
without ThinLTO, PGO, CFI or symbols (`scripts/build-env.ps1`), which
keeps links within hosted memory; no codec or branding flags are set. A full
six-target build can take multiple days depending on runner performance. Tree
artifacts (~13 GB per stage) are kept for 7 days and candidates for 14 days.
The standard Apple Silicon runner has 7 GiB of RAM, below CEF's recommended
16 GiB; its ability to finish these builds must be established in CI.

Locally, on a native trusted machine with at least 16 GiB RAM and 200 GiB free
disk (see CEF's
[automated build setup](https://github.com/chromiumembedded/cef/blob/8ea0c73b5dbed1389c8dafb911a98c41246bb8cb/docs/automated_build_setup.md)):

```sh
pwsh scripts/sync.ps1 -Directory /new/owned/dir -Target linux-x64
pwsh scripts/build.ps1 -Directory /new/owned/dir -Target linux-x64 -Deadline 4102444800
pwsh scripts/distrib.ps1 -Directory /new/owned/dir -Target linux-x64
```

The directory must not already exist; it is never cleaned or reused.

## Consuming a release from a cef-rs fork

Each release contains, per target, the original
`cef_binary_<version>_<platform>_minimal.tar.bz2`, `manifest-<target>.json`
(upstream pins, repository commit, patch identities, archive SHA-256) and a
combined `SHA256SUMS`.

An unpacked `binary_distrib` is **not** a cef-rs `CEF_PATH`. Download the
archive, verify `SHA256SUMS`, keep its canonical basename, then use
`export-cef-dir` from pinned
[cef-rs](https://github.com/tauri-apps/cef-rs/tree/9aa78c450489eddb828eb982eaee6c104a89d348/export-cef-dir):

```sh
export-cef-dir --archive cef_binary_..._linux64_minimal.tar.bz2 \
  --target x86_64-unknown-linux-gnu /path/per/patched/release
export CEF_PATH=/path/per/patched/release
```

This flattens `Release`/`Resources` and writes `archive.json`. CI smoke-tests
the exporter with both synthetic and release archives. A cef-rs fork can
instead download from the release URL in its build script; either way:

- Use a distinct `CEF_PATH` or cache directory per patched release. An invalid
  or too-new `archive.json` makes this cef-rs revision silently download
  **stock** CEF; IronRDP rejects stock CEF at startup.
- Never infer patch identity from CEF's API hash or `archive.json`; use the
  manifest's patch identities and archive checksum.
- On macOS, this cef-rs revision copies framework files but not symlinks; the
  fork must preserve or recreate the framework layout and sandbox/bootstrap
  resources.
- Upgrade cef-rs and these pins together.

## Updates

The daily `Watch` workflow compares the pinned release branch head with the
pinned CEF revision and keeps one open issue for review. It never updates pins,
opens PRs, triggers builds or ships binaries. Updating means editing
`pins.json` (and patch identities if patches change), then dispatching a build.
Milestone upgrades need an explicit decision and coordinated consumer changes.
